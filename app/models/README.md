# `app/models/` — SQLAlchemy tables

## Layout
- **`hotel_settings.py`** — one row per hotel. `hotel_id` (string, public identifier) is distinct from `id` (integer PK, used for FKs). Holds the AI engine choice (`ai_engine`) and the Fernet-encrypted API key (`api_key_encrypted` — see `app/security/crypto.py`). `is_test` hides test hotels (e.g. `prague`) from real end users. `hotel_skill_path` points to a git-tracked Markdown file with the hotel's own greeting text + tone instructions (see `app/knowledge/hotel_skill.py`); `None` means use the generic defaults.
- **`conversation_log.py`** — one row per chat turn. Deliberately anonymous: no guest identifier of any kind, only `hotel_id`, `region`, `question`, `answer`, `found_in_kb`, `ai_engine`, `created_at`.
- **`hotel_contact.py`** — `HotelContact`, many-to-one to `HotelSettings` via `hotel_settings_id`. A named person at the hotel (`name`, `role`, `phone`, `email`) plus `priority` — the order in which contacts will be asked to fill knowledge-base gaps once the phase 2 reception-feedback loop is built (lower number asked first; not enforced unique). Reverse side: `HotelSettings.contacts`.
- **`hotel_region_tag.py`** — `HotelRegionTag`, many-to-one to `HotelSettings` via `hotel_settings_id`. A single geographic tag string (e.g. `"nahariya"`, `"coast"`); a hotel has a list of these, unique per hotel (`uq_hotel_region_tag`). Reverse side: `HotelSettings.region_tags`. Consumed by `app/api/whatsapp_webhook.py` to resolve which knowledge-base regions apply to a hotel's inbound WhatsApp messages.
- **`hotel_messaging_settings.py`** — `HotelMessagingSettings`, one-to-one with `HotelSettings` via `hotel_settings_id` (unique). Optional per-hotel override of the WhatsApp provider/credentials (Twilio or Meta Cloud API) and the per-hotel daily send limit; any field left unset falls back to the global default in `app/config.py`. Twilio/Meta secrets are Fernet-encrypted the same way as the AI engine key. Reverse side: `HotelSettings.messaging` (`uselist=False`).
- **`message_rate_limit.py`** — `MessageRateLimitCounter`. One row per `(scope, scope_key, day)` — tracks today's WhatsApp send count per phone number, per hotel, and globally, to cap the bill. No FK: `scope_key` is a phone number, a `hotel_id`, or the literal string `"global"` depending on `scope`. Only today's rows matter; stale rows are harmless.
- **`guest_session.py`** — `GuestSession`, many-to-one to `HotelSettings` via `hotel_settings_id`, unique per `(hotel_settings_id, phone)`. A guest's current stay: `phone`, `check_in`/`check_out`, `welcome_sent_at`, and the scripted-flow state (`flow_state`, `trip_type` — see `app/messaging/flow.py`). Deliberately **no name or ID field** — matches the PII-minimization principle in `hotel_concierge_bot_plan.md` exactly (phone + vacation info only). Auto-deleted at checkout via `scripts/purge_expired_guest_sessions.py` (needs to actually be scheduled to run — see that script's docstring). Reverse side: `HotelSettings.guest_sessions`.

## Adding a table
1. New file here, class inherits `Base` (from `app/db.py`).
2. Import it in `__init__.py` and add it to `__all__`. This isn't just bookkeeping — relationships elsewhere use string forward-references (e.g. `Mapped["HotelContact"]`), and those only resolve once the class has actually been imported somewhere and registered on `Base`'s mapper registry.
3. If it points to `hotel_settings`, FK the integer `id` column, not the string `hotel_id` — follow the `hotel_settings_id` naming used by the existing FK tables above.

## Schema sync
No migration tool (no Alembic) — `app/db.py`'s `init_db()` calls `Base.metadata.create_all()` on startup and in tests, which creates any table that doesn't exist yet but does **not** alter existing tables. A genuine column/constraint change on an existing table needs a manual migration path once there's real data to preserve.
